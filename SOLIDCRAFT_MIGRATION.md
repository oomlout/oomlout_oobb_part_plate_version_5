# Plate project: additive SolidCraft migration

## Reset generated SolidCraft outputs

Run `action_delete_solidcraft_files.bat` to clear the generated true/3dpr SolidCraft files and their STEP, native STL, PNG and metadata companions from part folders. The next build regenerates missing native files. Use `action_delete_solidcraft_files.bat -DryRun` to preview targets.

SCAD outputs, part definitions, custom/manual files, sealed parts and build history are preserved. Cleanup refuses to run while a SolidCraft writer holds the build lock. The batch file works from any current directory; its implementation is in `components/solidcraft_cleanup/working.ps1`.

## Generate missing native files only

SolidCraft generation checks `parts/<part-id>/true.solidcraft` and `3dpr.solidcraft` separately. If the requested native file exists, that mode is skipped before recipe loading or CAD work. Only missing native files are generated. This applies to direct `working_solidcraft.py`, make-all and the SolidCraft-only action through their shared pipeline.

This is a file-existence rule: recipe changes, verification/export flags or missing PNG/STEP/STL files do not force regeneration. To regenerate a mode, remove its published `.solidcraft` file and run again. Old attempt files and manifests do not prevent rebuilding when the published native file is missing. Existing sealed-part protection still takes precedence.

## Optional SolidCraft verification

Verification defaults to **off**, separately from export selection. Both make action scripts declare:

```python
kwargs["verify_solidcraft"] = kwargs.get("verify_solidcraft", False)
```

Change that default to True, pass `verify_solidcraft=True` to the action's `main()`, or use `python working_solidcraft.py --verify`. `working.run()` extracts the ordinary kwarg before other actions receive it. Direct native scripts also declare `VERIFY_SOLIDCRAFT = False`.

With verification off, requested SolidCraft/STEP/STL/PNG files still generate and publish immediately. Reference geometry, measurement comparisons, reopened-file checks, edited variants and STEP reimport are skipped. Command errors and native structural health still fail the build. Manifests explicitly record `verify_solidcraft: false` and `verification.status: not_requested`.

With verification on, native-only runs check reference measurements and saved-file reopening; runs with extras additionally perform the existing STEP comparisons, parameter edits and reimport checks. `--extras` selects exports only; it no longer enables verification implicitly.

## Default native output (updated)

`action_make_all.py` and `action_make_solidcraft.py` enable native SolidCraft, STEP, PNG and STL outputs by default. They set ordinary `kwargs["export_extras"]` and `kwargs["export_stl"]` to True when not supplied. `working.run()` extracts these flags into the internal SolidCraft options before calling other actions; absent flags default to False. Explicit flat kwargs take precedence over legacy context values, and filters/modes are preserved. This differs intentionally from running `working_solidcraft.py` directly.

`python working_solidcraft.py` now generates only `true.solidcraft` and `3dpr.solidcraft` in each enabled part's folder. `EXPORT_EXTRAS = False` and `EXPORT_STL = False` are visible in the recipe file. Add `--extras` for STEP and PNG previews with extended edit/export verification; add `--stl` for STL independently. Python callers can use `solidcraft_context={"export_extras": True}`.

Ordinary generation still checks native measurements, constrained sketches and saved-document reopening. Diagnostic JSON and publication manifests remain for build tracking. Existing PNG/STEP/STL files are preserved but are not regenerated by the default command. The earlier sections below describe the migration history and optional full export route.

Migration date: 25 October 2026. Pilot part:
`oobb_part_plate_basic_3_width_3_height_3_depth`.

## Editing the native recipe

`working_solidcraft.get_plate` is near the top of `working_solidcraft.py`.
It defines each component with `p3 = copy.deepcopy(kwargs)`, individual
`p3["..."] = ...` assignments, and `oobb.append_full(thing, **p3)` calls,
just like the SCAD authoring flow. Edit those assignments to change native geometry. The SCAD
recipe remains separately editable. The same authoring pattern is in
`C:\gh\project_base\working_solidcraft.py`.

Each component starts with a fresh `p3 = copy.deepcopy(kwargs)` and then assigns
its fields. This preserves inherited part options while making the
component's overrides visible. Keep the hole array's `p3["depth"]` equal to plate depth.
The single-cell base uses `oobb_plate`; larger bases use
`oobb_rounded_rectangle_rounded`. Build, verification and publication support
is below the recipes; reusable CAD mechanics remain in helper components.

This authoring refactor preserves the component requests and does not require
regenerating the existing CAD files. Use the normal make-all entry for new builds.

## Current CAD structure: reusable definitions and finite-depth holes

The second migration pass replaces the original per-hole sketches with **two
position sketches and two native Hole features** on the 3x3x3 plate:

- `oobb_hole_m3_positions` / `oobb_hole_m3_holes`, in the `oobb_hole_m3` folder;
- `oobb_hole_m6_positions` / `oobb_hole_m6_holes`, in the `oobb_hole_m6` folder.

Edit `oobb_hole_m3_radius` or `oobb_hole_m6_radius` to change the entire family.
Both hole features use **`plate_thickness`**, initially 3 mm, as their exact depth.
Their sketches start on the top face at `array_z + plate_thickness`; a thickness
edit moves that plane and changes the cut depth together. The plate has eight
timeline features in total. The two placement sketches are fully constrained.

The underlying OOBB request contains 25 M3 positions and nine M6 positions. Nine
small holes are coincident with, and hidden inside, the large holes; the finished
part has **25 visible holes**, not 34. Retain those source positions so family
parameter edits keep the original Boolean meaning. Drill small holes first, then
enlarge the nine main positions. Use explicit sketch point IDs, an explicit simple
hole type, and a top-face start; do not let the engine guess drilling direction
from points that may already be in a hole.

Other supported repeated holes, nuts and socket-cap screw geometry use named
master profiles and associative Move/Copy instances. Screw heads and shafts are
separate named roles of the screw definition; hexagonal nut pockets have their
own reusable profile. A shared radius edit rebuilds every instance. Different
depths, radii, cross sections or local Z anchors are separate definition variants.
Only geometry already supported by this helper is admitted; this does not add
arbitrary threads or new screw-head types.

`<mode>_solidcraft_structure.json` lists definitions, instance counts, parameters,
sketch count, native Hole count and depth policies. The full plan, placements and
command evidence remain in the immutable attempt directory. Definitions have
named timeline folders. Generic copied instances retain readable placement names;
they are not forced into noncontiguous folders, which SolidCraft disallows.

### Scope of the longstanding depth fix

**No OOBB version 5 source files are changed.** The shared stdlib-only adapter
`oobb_solidcraft/hole_arrays.py` corrects expanded `oobb_holes` leaves to the array's
explicit depth and Z origin. The construction worker uses it for native output;
this project's `working_scad.main()` uses the same adapter in a scoped context
for SCAD output, restoring the original API afterward. Thus the 3x3x3 SCAD cutters
also run from Z=0 to Z=3 rather than Z=-100 to Z=100.

The correction applies only to `oobb_holes`. Individual holes, bearing seats,
screw features and nut pockets retain their intentional depths. Missing explicit
depth, rotated arrays or unrecognized array geometry fail clearly rather than
guessing an axis. Other OOBB projects do not acquire the SCAD adapter implicitly.
This project's corrected SCAD path now also needs the configured helper root,
although the adapter itself needs no CAD packages in the legacy Python.

### Failed approaches and verification

Associative copied cutters ending exactly at both plate faces caused SolidCraft
to retry a large Boolean with a small displacement/rotation. The health checks
correctly rejected that result. Native multi-point Hole features avoid that
problem; do not reintroduce huge cutter depths or relax accuracy checks to hide it.
Explicitly fix the position sketch points: numeric strings alone do not constrain
them in the tested SolidCraft version.

The shared backend now edits every reusable radial definition after reopen,
checks the entire rebuilt shape against the independent reference, exports STEP,
saves the edited native document, and reopens it again. The real OOBB repeated
hardware fixture passed for two socket-cap screws and two hex nut pockets:
all three shared roles (head, shaft, hex pocket) updated both instances, with zero
STEP/reference symmetric difference. Evidence is under the helper's
`build/cadlike_hardware/attempts/4087743cdc58`.

The finite-depth adapter and family compiler pass all 390 combinations in the
195-part catalog preflight. Every combination compiles to three logical geometry
definitions (base, M3, M6), rather than one definition per hole. Full native export
of the catalog is still left to the user's make-all run. Regression suites now
contain 18 helper tests and 5 project orchestration tests.

Final reusable-feature regeneration succeeded in `true` attempt `22a0e195a9d3`
and `3dpr` attempt `dc94940ac558`. Compared with the first migration, the plate

Both family-radius edits passed exact geometry and saved/reopened checks in both

## Geometry decisions and failed approaches worth remembering

The 3x3x3 plate is **44 x 44 x 3 mm**, centered in XY, with Z from 0 to 3 mm.
Its outline has 5 mm plan-view corner radius and 1.5 mm upper/lower edge rounding.
The 25 through-holes comprise nine large holes on the 15 mm grid and sixteen
smaller intermediate holes on the 7.5 mm grid. Mode-specific radii come from the
actual builder and catalog, not newly typed nominal measurements.

The old `oobb_rounded_rectangle_rounded` component expands into rounded prisms,
sideways cylinders and corner toruses. At 3 mm thickness it includes a
zero-thickness middle prism and duplicate coincident rim solids. A zero-volume
prism contributes nothing to the printable solid: omit it with an explicit build
warning. Exact duplicate union operands can be removed because union is idempotent.
For a plain rounded rectangle, the equal-radius four-cylinder hull is represented
exactly as two rectangles and four cylinders. General hulls and omitted corners
are still rejected, rather than silently approximated.

**Do not simply join all the tangent rim pieces in SolidCraft.** The first pilot
attempts failed Boolean union, or produced a kernel warning about displacement /
rotation retries. Such warnings fail the native health check. The working native
construction is one box, four vertical 5 mm fillets, then the top and bottom rim
fillets at the exact 1.5 mm radius. SolidCraft follows the tangent rim chain from
one exact edge midpoint per rim. Then translate to the legacy XY origin and apply
the native hole-family features. The native plan retains the expanded legacy CSG for
audit, and the executed SCAD output is compared to the finished geometry.

Only the recognized component request with uniform intent is collapsed into this
native construction. Require `corner_radius > rim_radius`, positive dimensions,
and `depth >= 2 * rim_radius`; do not silently reduce radii to make a kernel happy.
Outer transforms and Boolean polarity remain in the normal grouped tree.
The native model's dimensions, corner radius and rim radius are named parameters;
each hole family has a named radius and shares the plate depth. Native reopen/edit
testing changes family radii in separate verification documents, never in the deliverable.

Legacy `oring.id` is misleadingly named: its renderer uses
`major_radius = id + depth/2`, and `minor_radius = depth/2`.
Do not divide `id` by two during migration. The plate's corner toruses therefore
have major radius 3.5 mm and minor radius 1.5 mm.

## Independent validation details

The helper checks feature/sketch health, exact native dimensions, valid STEP
solids, symmetric Boolean differences, STL watertightness/winding/topology and
deterministic surface samples. It reopens the native file, changes a named hole
radius by 0.2 mm, verifies that rebuilt shape, saves the verification variant,
reopens it again, and separately imports the original STEP.

Two validator issues surfaced in this pilot:

- OCCT 7.7 cannot directly fillet a prism at exactly half its thickness. The
  independent oracle builds a taller filleted prism, extracts the two rounded
  end sections, and rejoins them after removing the straight middle section.
  This is exact geometry; no epsilon is subtracted from the radius. Analytic
  cross-section integration checks the unperforated volume for both 3 and 6 mm.
- OCCT point-to-shape extrema can miss a trimmed torus across a periodic UV seam.
  For failed samples, project onto periodic surfaces, wrap UV to the face's trim
  interval, and require the projection to classify inside/on the trimmed face.
  Do not accept distance to an untrimmed infinite surface alone.

SCAD `$fn=50` tessellates both angles of a torus. Its conservative chord-error
bound uses `(major_radius + 2 * minor_radius) * (1 - cos(pi/50))`, plus the
existing 0.002 mm numeric allowance. A cylinder-only sagitta bound is insufficient
for the rounded corners. Native STL uses the existing scale-dependent tolerance.
Exact STEP checks remain much tighter (symmetric difference below 0.001 mm3).

Legacy `save_type="all"` asks OpenSCAD for DXF/SVG of a 3D object, which prints
"Current top level object is not a 2D object." Those pre-existing 3D-to-2D export
messages do not describe the dedicated `laser_flat.dxf` export. Verify the actual
SCAD, STL, PNG and flattened laser files rather than treating log silence as proof.

## Publication, diagnosis and hand editing

Attempts are immutable under `build/solidcraft/runs/attempts/<id>/`. Inspect
`build/solidcraft/runs/latest_run.json`, each `build_manifest.json`, `failure.txt`,
`command_results.json` and session logs. Failed attempts are intentionally retained.
`latest_success.json` only advances for an entirely successful selected run.

Only successful, verified mode results are copied into their part folder. Verify
export hashes, stage replacement files, publish them, and write the part manifest
last. Each file replacement is atomic; a multi-file set is not one filesystem
transaction, so consumers should check the manifest's hashes. A failed mode does
not overwrite its old published files and the command exits nonzero. Successful
modes may publish even if another mode fails. The project writer lock covers both
generation and publication; never remove it while its PID is still active.

Native regeneration is serial and includes multiple reopen/export checks for each
part/mode. The full catalog takes substantially longer than a SCAD-only build.
This pilot did not run full make-all, change all catalog output files, commit, or
push. Existing manual files and unrelated part folders are not migration targets.

# Per-part output switches

## Separately editable native plate recipe

`working_solidcraft.get_plate(thing, **kwargs)` owns the native plate recipe.
It starts with the same dictionaries and `oobb.append_full()` calls as
`working_scad.get_plate`. `oobb_details.oobb_type: plate` selects `get_plate`
in each backend. `get_basic` delegates to `get_plate` only for compatibility
with older definitions without a type, so existing part IDs stay valid. The native
launcher now explicitly passes `working_solidcraft.py` as its builder. Edit that
function to change native geometry independently; SCAD keeps its own recipe.

Keep the ordinary `width`, `height`, `depth`, `pos`, `rot` and `prepare_print`
arguments. Geometry recipes describe plate and hole requests; shared helper
components continue to own dimension resolution, named CAD families, finite
hole depth, command execution and verification. No SolidCraft session or export
calls belong in `get_plate`.

The native verification SCAD is built from the native recipe's expanded
definition. It verifies translation of that recipe; after an intentional edit,
it does not assert that the separate production SCAD recipe remains identical.

## Output flags

The `oobb_details` definition now includes two independent boolean settings:

```yaml
oobb_details:
  oobb_type: plate
  oobb_name: basic
  width: 3
  height: 3
  depth: 3
  run_scad: true
  run_solidcraft: true
```

Set either to `false` to skip that part's corresponding output route. Missing
flags default to `true` for existing projects; quoted strings and numbers are
rejected. Global `working.run(run_scad=..., run_solidcraft=...)` controls remain
in effect. Setting both false leaves existing generated files in place.

Persistent defaults live in `working_oomp_populate.apply_taxonomy`. Individual
options can supply `run_scad` and `run_solidcraft` before that function creates
their `oobb_details`. Editing generated `working.yaml` is useful for a direct
build, but a later population may overwrite it. The existing full
`oobb_details` override in `working_manual.yaml` remains available.

Shared selection and validation live in the helper's
`components/build_policy/working.py`, distributed unchanged into this project's
and project_base's matching component folders. The ordinary Python SCAD route
uses the stdlib-only `working_cad.py` facade. The native pipeline records disabled
part/modes as skipped and never publishes them. All-disabled selections succeed
without replacing the previous success index. Unmatched filters still fail.
Flags are stripped before geometry construction, including stale saved kwargs.

Native generation calls its own editable geometry function and verifies exact geometry,
native reopening and parameter edits. `run_scad` controls the separate SCAD output route;
it does not disable native verification. A SCAD comparison is an explicit optional audit.

To add a type, declare `oobb_type: bracket` during population and implement
`get_bracket(thing, **kwargs)` in each enabled backend. No dispatcher registration
is required. Missing explicit-type routines raise an error. The same contract,
starter plate functions, per-part flags and population example are installed in
`C:\gh\project_base`; see its `CAD_BUILDING.md`.

## Optional hardware rendering detail

`RENDER_DETAIL = False` in `working_solidcraft.py` keeps ordinary generation unchanged. Set it to True to add detail to positive screws, nuts and bearings. See [the rendering switch guide](SOLIDCRAFT_RENDER_DETAIL.md) for per-part overrides and supported details.


## Interrupted runs and the no-STL default

`python working_solidcraft.py` builds all populated, enabled parts, with no native STL export. Both this project and project_base use the shared `components/project_launcher` implementation. Dead writer locks recover automatically; a second active writer is rejected. Large hole arrays retain their named sketches and shared radius parameters. Coincident cutters use the larger of their two radii, and ordinary plates receive exterior rounding after drilling to avoid large-plate Boolean timeouts. The CAD timeout remains configurable in the helper backend YAML. Native generation and exact validation can still take time on large plates.


## Files appear as each native build completes

Each verified part/mode is copied into `parts/<part-id>/` immediately, before the next build starts. The console prints `Published ...` with the destination, then reports success. Files no longer wait for the entire batch to finish. The live progress index is `build/solidcraft/runs/latest_run.json`; failed publication is reported as a failed result.
